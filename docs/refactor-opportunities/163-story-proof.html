What the story left behind

Story #163 did what it set out to do, and it did it without a line of new code. scripts/worker_state.py, scripts/close_item.py, scripts/merge_train.py and scripts/tracker.py are byte-identical. The parent story wears the phase:e2e label a leaf proof already used, so the Worker watch reads the new flow through a branch it already had. No new outcome, no new label string, no new exit code, no new config field. That is the claim in ADR 0047, and the suite proves it: 166 tests pass with no new expectation.

So the friction this story introduced is not in a module. It is in the test surface. The story's whole deliverable is prose, and it added its largest artifact in the one file format this repo cannot check.

Candidate 1

No suite reads an HTML file, and three documents promise a work item that is not there

Strong

Files

  • scripts/test_links.py — 382 lines, walks **/*.md
  • docs/architecture.html — 1068 lines, added by this story
  • docs/skill-state-and-roadmap.html — 1159 lines, rewritten by this story
  • docs/refactor-opportunities/ — the report directory ADR 0048 created, plus its hand-written index

Problem

This repo's stated main failure mode is a dangling cross-reference, and scripts/test_links.py exists to make that a failing test instead of a merged defect. It walks Markdown only. This story added 2227 lines of HTML that hold the target design and the wave order for the next five stories, and nothing checks a link or an anchor in either page.

Three documents each name this as separate work, and each one assumes another owner has it:

WhereWhat it says
ADR 0047, Consequences“A Markdown-plus-HTML link walk is work of its own.”
#163, Out of Scope“An HTML link checker. Named above as its own work item.”
#201, Out of Scope“That is a named limit in ADR 0047 and its own work item.”

No such work item exists. A search of every issue, open and closed, returns none. So the promise is the only owner, and a promise has no exit code.

The cost is already measured. The worker on #168 read all 2227 lines by hand, because the item told it to. That read found four wrong facts on the roadmap page, including a row that said the bump was a patch while its own table said minor. A human read caught them once. Nothing makes the next read happen.

Solution

Give scripts/test_links.py a second pass over docs/**/*.html, reusing the link extraction and the target resolution it already has. Three assertions cover every promise above:

  1. every internal anchor on a page resolves to an id on that page,
  2. every relative link target exists on disk,
  3. every report in docs/refactor-opportunities/ has a row in that directory's README.md, and every row points at a file that is there.

The shallow version to avoid is a second module with its own walker. That duplicates the resolution rules, and two walkers that disagree about what a relative path means is a worse failure than no walker at all. The interface is the test surface here: one walker, two file extensions.

Benefits

  • Locality. One file answers “does every cross-reference in this repo resolve”, for both formats. Today the answer is split between a test and a habit.
  • Leverage. make quick already runs this suite on every item, so the new pass costs no new command, no new config field and no new gate row.
  • It retires a named limit instead of carrying it. ADR 0047 and #201 both stop needing their exception.
  • Tests improve where the repo's product is. The product is prose. Two of its four biggest files are currently unread by any command.

Candidate 2

The story proof is defined in the one repo that can never run it

Worth exploring

Files

  • orchestrator/SKILL.md — ### The story proof, 67 lines, a seven-step flow
  • docs/agents/orchestrator.md — run_recipe: "", blank by design
  • orchestrator/references/examples/ — the worked traces

Problem

The reachability gate for a proof is a non-blank run_recipe, or an evidence bar that asks for UI proof. This repo has neither, and #163 says so in its own decision: “This repo is the blank case, so no story here reaches a story proof.” Reusing the existing gate is the right call, and it has one consequence nobody wrote down. The flow's first real execution happens in a stranger's repo, on a story that matters, with no rehearsal anywhere.

Every other flow in this skill has been run here at least once. The spawn, the wake, the review loop, the close transaction and the merge train all have live traces. This one has seven ordered steps, two artifacts, a failure path and an automation repoint, and not one of them has ever fired.

Solution

Two shapes, and the cheap one probably wins. Add a worked trace to orchestrator/references/examples/ that walks the seven steps against a named fictional project with a non-blank run_recipe, the way routed-run.md already does for the two lanes. That is prose, so scripts/test_links.py covers its cross-references the moment it lands. The expensive shape is a fixture repo with a bootable app, which buys a real exit code and costs a second project to maintain.

Benefits

  • Locality. A reader who has to run a story proof reads one trace instead of assembling it from four sections and two ADRs.
  • It is the same mitigation this repo already chose for routing, so it introduces no new pattern.
  • The gaps a trace exposes are found before a user finds them.

Why this is not Strong. The rating is honest about leverage. A trace is documentation about documentation, and ADR 0032 already accepts that enforcement here is documentary. It buys confidence, not an exit code. Candidate 1 buys an exit code.

Dropped, because the migration plan already owns them

Three further findings are real, and each one is already work. A gate that files them again would put two items on one problem, which is the drift this directory exists to stop.

Top recommendation

Candidate 1, the HTML pass on scripts/test_links.py. It is the only finding here that no existing work item owns, it is the only one that produces an exit code, and it is the smallest of the three by diff. It also reuses a module that already passes 166 tests, so it climbs no new rung.

There is a timing reason too. Waves 1 to 5 move more Markdown files than any story so far, and #201 says to run the link test after every single move. Those waves also keep editing the two HTML pages, because both pages describe the target the waves are walking toward. Landing the HTML pass first means every one of those edits is checked. Landing it after 1.0.0 means five waves of unchecked edits to the two documents that define the plan.
