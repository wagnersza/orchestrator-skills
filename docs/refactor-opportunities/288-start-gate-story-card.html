2. The start gate owns two of its three rows, so start --item N disagrees with the tick

Strong

Files

  • scripts/worker_state.py:1418 start_gate — answers row 1 and row 3
  • scripts/worker_state.py:1811-1816 — row 2 lives here, as a raw label read inside queue_candidates
  • scripts/worker_state.py:1504-1523 start — the CLI answer, one item, one board read
  • orchestrator/SKILL.md:269-283 — tells a session this seam answers the gate

Problem

ADR 0062's table has three rows. start_gate sees one item and its labels, so it cannot know whether that item is a child of an authorised story. Row 2 needs the ## Parent walk and the parent's card, so it was implemented inside queue_candidates as a set comprehension over the labels.

The concrete failure: run worker_state.py start --item <child> for a labelled child of a story whose card sits in To do. It prints no-fact: work item #N carries the ready-for-agent label, and it has no card in the 'To do' column and exits 1, while the same tick, in the same minute, starts that child. A session that trusts the seam (as SKILL.md:269 instructs) refuses the work the automation performs. The module named "the start gate" is not the gate.

Solution

One function resolves the whole table over one open-items read. queue_plan already builds by_number and children, so start makes the same list read and asks the same function. The cheaper variant keeps start_gate per-item and adds a fourth answer for "authorised through my parent", resolved only by the caller that holds the tree. But then the three-answer vocabulary grows and the table is still split.

Benefits

Locality: one function to read when asking "what starts this item", instead of a gate plus a set comprehension. Leverage: the fourth narrowing of this table edits one place. Tests: the row-2 and row-3 cases move out of the queue_cli subprocess and into the in-process self.gate helper, which is already where row 1 is proved.

Before / After

Before

start --item N ──> start_gate └─> rows 1, 3 (row 2 answered wrong) queue tick ──> start_gate └─> queue_candidates └─> rows 1, 2, 3

After

start --item N ──┐ ├─> one gate over queue tick ──────┘ (item, tree) └─> rows 1, 2, 3 one answer, two callers

Duplicate check and ADR conflict

New. Adjacent to #250, which lifts the CLI plane out of worker_state.py, but that item is about argument plumbing and not about which rows the gate answers. No ADR is reversed: ADR 0062 says "This ADR records the contract and wires nothing", so it never says what start --item N returns for row 2. Reopening is not warranted. An amendment naming the seam's answer for row 2 is.

3. "Kind first" is not first: the no-board branch decides before the kind is read

Worth exploring

Files

  • scripts/worker_state.py:1423 — the docstring claim, "the gate reads the item's kind first"
  • scripts/worker_state.py:1460-1470 — the label read, then the no-board early return
  • scripts/worker_state.py:1490 — the kind, read third
  • orchestrator/docs/adr/0062-a-story-card-authorises-its-run.md:48-49 · orchestrator/CONTEXT.md:237-239

Problem

The gate has two disjoint decision tables, and only one of them knows the item's kind. On a tracker that names no board (a configuration this repo calls supported), start_gate returns on the label alone. So a user-story is authorised only if it wears ready-for-agent. That is the option ADR 0062 rejected, made mandatory. ADR 0062 reads the other way, and the docstring repeats it, but the code authorises a labelled story and descends into its children. No test covers a story in that mode: the no-board case uses a leaf fixture.

Solution

Answer the open question first. On a no-board tracker, does a story authorise its run on the label, or does the fallback become leaf-only? Then read the kind before the config check, so there is one table and the docstring is true.

Benefits

Locality: one decision table instead of two, and the "kind first" claim becomes checkable. Tests: one case, a user-story with no board coordinates, which today has no answer to assert.

Before / After

Before

labelled? ─> no board? ─> board read │ └─> kind? ─> rows 1/3 └─> label only (kind never read)

After

kind? ─> no board? ─> the row that kind owns, board or no board one table, docstring true

Duplicate check and ADR conflict

New. Contradicts ADR 0062 against itself: its no-board sentence says a story authorises nothing through a column that does not exist, and its rejected-options list forbids a label on a story. Reopening is warranted, as an amendment naming the no-board row for a user-story, and never as a reversal. Nothing is broken on this repo today, because this repo has a board.

4. Every candidate wears ready-for-agent, and two roads prove it separately

Worth exploring

Files

  • scripts/worker_state.py:1714-1724 startable — reads the labels for the story and owned facts, not for the ready label
  • scripts/worker_state.py:1811-1816 — the story road checks the label
  • scripts/worker_state.py:1818-1823 — the standalone road gets it implied by the gate answer

Problem

After ADR 0062 one invariant holds on both roads: a candidate that is not a spec carries ready-for-agent. Row 3 gets it from the gate answer, the no-board fallback gets it from the gate answer, and row 2 gets it from a filter. So the rule "an unlabelled item stays stopped" has two proofs in two shapes. And startable, the function whose name claims to answer "is this a leaf a tick can start now", reads three of the four facts. A reader has to compose the gate answer's meaning with a set comprehension to see the fourth.

Solution

Move the ready-label check into startable, which already holds the labels. The story road then collapses to the descendants walk. Behaviour is byte-identical: on every branch, a non-story item that answers the start value is labelled.

Benefits

Locality: one function answers "can this leaf start", for both roads. Leverage: startable becomes a pure predicate over three arguments with a direct unit test, which is what #278 asks for the untested functions. Tests: the existing subprocess cases keep passing unchanged, and that is the proof the move preserves behaviour.

Before / After

Before

candidate = ( in from_stories [label checked HERE] OR gate == START [label implied] ) AND startable(no spec, unowned, unblocked)

After

candidate = ( in descendants(authorised) OR gate == START ) AND startable(labelled, no spec, unowned, unblocked)

Duplicate check and ADR conflict

New. #278 would give startable its direct test, and this candidate changes what that test asserts. So run this one first if both run. No ADR conflict: it restates ADR 0062's rows without moving one.
