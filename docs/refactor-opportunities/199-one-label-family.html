What user story #199 left behind

Story #199 landed as three work items: #208 (the tick computes the position), #209 (one work-state family, four values) and #213 (nothing writes the board). This report reads the state those three items left across the seams in scripts/, the hook plane in hooks/, and the skill body.

Two of the three candidates below are the same bug class that #186 reported and #213 closed: one recipe with two implementations. #213 deleted the duplicate inside the Tracker adapter. Candidate 1

The label write has a denial and no performer

Strong

Files

  • hooks/refuse.py:167 — label_denial
  • hooks/refuse.py:184 — teardown_denial
  • scripts/close_item.py:303 — the only label write in the repo
  • orchestrator/SKILL.md — the spawn claim and the review-state transition

Problem

hooks/refuse.py denies every command that writes a Work-state label, with no exception, and its message says "Run scripts/close_item.py for the labels of a close." That command is itself denied: label_denial reads the words of the command and never asks who the caller is. Its sibling teardown_denial asks exactly that question, seventeen lines below, and exempts the seam by name.

The second half is worse. Story #199 assigns in-progress to "the session at spawn, and spawn_item.py from wave 4", and to-review to "the session at the finish, and worker_state.py from wave 3". Neither seam exists yet. So for the whole of wave 2 there is a denial with no performer: the two transitions a run depends on cannot be written by anybody.

Observed three times while closing this story.

The spawn claim on #213, the review-state write on #213, and the --remove-label argument of the close on #209 were all denied. #209 is closed wearing to-review and #213 is closed wearing ready-for-agent.

Solution

Make the label write a seam with one entry point, and let the hook exempt that seam the way it already exempts the teardown. Concretely: one scripts/work_state.py that owns the swap, built on the Tracker.label_argv that already exists, with a plan-then-execute shape copied from close_item.py. Then label_denial gains the same caller test teardown_denial has, and the denial message names a command that runs. The two seams wave 3 and wave 4 promise then call that module instead of adding a third label writer.

Benefits

  • Locality. The swap rule, the "never stack" invariant and the vocabulary sit in one module. Today the invariant is stated in docs/agents/issue-tracker.md and enforced nowhere.
  • Leverage. One test asserts the invariant the story was written to buy: exactly one work-state label after every transition. That test cannot be written today, because no function performs a transition.
  • The hook plane law holds again. A hook answers, and a seam performs (ADR 0051) is currently half true: the hook answers, and nothing performs.

Candidate 2

The hook plane re-reads every fact the seams already read

Strong

Files

  • hooks/refuse.py · hooks/record.py · hooks/context.py
  • scripts/worker_state.py · scripts/tracker.py

Problem

The three hooks import nothing from each other and nothing from scripts/. Every fact about the repo is therefore read once per hook, and once more in worker_state.py. Six concepts, thirteen implementations:

Two copies are already not identical. work_state_labels parses the ## Work-state labels table with a regex on the second cell in both files, so a change to that table's shape breaks two parsers on different days. gate_commands carries the same three-layer key tuple and the same GATE_LINE regex in two files, and both restate that layer 5 is not a Gate.

Solution

One deep module — scripts/repo_facts.py — whose interface is the questions, not the files: project_dir(), orchestrated(root), item_number(root), work_state_labels(root), gate_commands(root), head_sha(root). Each of the three hooks imports it with the same two-form try/except ImportError shim worker_state.py already uses for tracker.py, so both invocation forms keep working (ADR 0034).

Benefits

  • The deletion test says "concentrates". Delete the module and thirteen implementations come back. That is the signal.
  • Locality. A change to the gates: block shape, or to the work-state table, is one edit and one test.
  • The interface becomes the test surface. Today each hook's suite builds its own fixture repo to test its own copy. One suite over one module replaces three partial ones.

Candidate 3

One gate verdict, three implementations, three answers

Strong

Files

  • scripts/worker_state.py:423 · :480 — gate_runs, unproven_gates
  • hooks/refuse.py:272 · :311 — latest_runs, not_green
  • hooks/context.py:160 — gate_verdict

Problem

One question — does the Gate record hold a green line for this command at the current HEAD — is answered by three separate walks over the same .orchestrator/gates-<item>.jsonl file. All three decide when to stop at a malformed line, all three carry a SHA_PREFIX floor, and all three pick "the newest line of a command" as the verdict.

They have already diverged. worker_state.gate_runs rejects a line missing any of the four GATE_KEYS; refuse.latest_runs accepts any JSON object and reads the keys it wants. So a record whose lines dropped utc reads as malformed to the tick and as green to the push block. The push then goes through and the item stops at gates-unproven — the two halves of one contract disagreeing about the same file.

This is #186's finding, one layer up. #213 closed #186 by deleting one of two implementations of a board recipe. The same class survives here, at three copies instead of two, because the record format's one home is prose in references/quality-gates.md and not code.

Solution

A scripts/gate_record.py whose interface is the two questions the callers actually ask: verdict(path, command, head) returning the one reason it is not green or an empty string, and append(path, command, code, head) for record.py. The four causes and their wording then live once, and the gates-unproven line, the push-block message and the session-start fact all quote the same string.

Benefits

  • Locality. The format's writer and its three readers become one module. Today the writer is a hook and the readers are three strangers.
  • Leverage. The divergence above becomes untestable rather than untested: one function cannot answer two ways.
  • Testability. One table-driven suite over the four causes replaces three partial suites, each of which currently covers its own copy only.

Candidate 4

The Tracker adapter has two interfaces wearing one name

Worth exploring

Files

  • scripts/tracker.py:97 — class Tracker

Problem

Tracker mixes two kinds of method with no marker between them. item_facts, issue, pull_request and board_status run a command and return a fact. label_argv, close_argv, comment_argv, closing_note_argv and pr_read_argv return an argv the caller must then hand back to write(). A caller has to know which is which, and the fixture branch is written twice per concept as a result: once inside the reader, once inside write().

The reason the split exists is real: close_item.py prints its plan before it runs it, so it needs the argv as a value. That is a good reason for a plan object, and a weaker one for nine sibling methods that return two different kinds of thing.

Solution

Name the two halves. Keep Tracker for the questions, and give the writes a small TrackerWrite value with an argv, a name and a run(). A plan then holds a list of those and prints them; an executor calls run(). The _argv suffix stops being the reader's only clue.

Benefits

  • Leverage. Candidate 1's new label seam wants exactly this shape: plan the swap, print it, then run it. Doing candidate 4 first makes candidate 1 smaller.
  • Locality. The fixture branch moves into one place instead of one per write.

Note: this does not contradict ADR 0040, which put every tracker command behind one adapter. The adapter stays. This only names the two shapes of thing it returns.

Candidate 5

A parameter with a branch nothing can reach

Speculative

Files

  • scripts/worker_state.py:605 — position_of(..., verdict_written=None)

Problem

position_of takes a fourth argument, verdict_written, and branches on it. Its own docstring says why nobody passes it: "The Tracker adapter answers comment bodies and no dates, so a tick passes nothing here." The one production caller at line 801 passes three arguments. So the IMPLEMENTATION branch after a dated verdict is dead flexibility built for a fact the adapter does not yet return.

Solution

Either delete the parameter until item_facts returns comment dates, or add the date to item_facts now and make the branch live. Both are small. The deletion test is genuinely ambiguous here, which is why this is speculative rather than strong: the parameter costs almost nothing, and wave 3 may want it.

Worth raising only because the branch is documented as unreachable in the same paragraph that specifies it. A reader cannot tell whether it is a bug or a plan.

Top recommendation

Candidate 1, and it is not close

Candidates 2 and 3 are the deeper architectural wins. Candidate 1 is a live outage. The hook plane currently denies a write that no code in the repo can perform, so every transition of the label vocabulary story #199 just shipped has to be done by hand or skipped. Two items closed during this very story are wearing the wrong label because of it.

Do candidate 1 first, and take the small version: give label_denial the caller test teardown_denial already has, and add the label swap to a seam. Then candidate 3, because it has an observable divergence rather than a theoretical one. Then candidate 2, which is the largest diff and the one that stops the class coming back.
