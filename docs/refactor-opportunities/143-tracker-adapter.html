What the story left behind

Story #143 did what it set out to do. scripts/tracker.py is a deep module: one class, four values, and every place two trackers disagree is a branch inside the one method that differs. The deletion test passes cleanly on it. Delete the adapter and the difference does not move, it multiplies back into both seams.

The friction is not in the adapter. It is in the interface the two older seams present to it, and to their own tests. scripts/tracker.py arrived with an in-process test suite that imports it. scripts/worker_state.py and scripts/close_item.py still have only one test surface each: their own command line.

scripts/test_tracker.py       from scripts import tracker      in-process, 19 cases
scripts/test_close_item.py    subprocess.run([sys.executable...]) argv only, 28 cases
scripts/test_worker_state.py  subprocess.run([sys.executable...]) argv only, 65 cases

That asymmetry is what this report is about. It is also why thresholds.coverage in docs/agents/orchestrator.md is blank, with the reason written next to it: “both seams drive through subprocess, and in-process line coverage reads 0%”. That is a real note about a real limit, and one candidate below is the way to stop it being permanent.

Candidate 1

The tick predicate has no callable interface

Strong

Files

  • scripts/worker_state.py — lines 591, 701, 779, 878, 903, 921
  • scripts/test_worker_state.py — line 273, run_seam

Problem

Four values — repo, fixture, tracker_cli, tracker_host — exist for one purpose: to construct a Tracker adapter. The seam threads all four down five levels and then constructs that adapter three separate times, at three different depths, each from a different subset of the four.

line 822

Tracker(cli, host, repo, fixture)

all four

line 897

Tracker(cli, host, repo)

three, no fixture

line 621

Tracker(fixture=fixture)

one, and it drops the other three

The parameter count is the measurement:

FunctionParametersBar
wake18
phase15
transition8
deliver8
wake_targets8
merge_requested6

wake() forwards 15 arguments positionally into phase() in one call (line 949). Nothing names them at the call site. A reordered parameter type-checks, runs, and prints a plausible line. That is exactly this repo’s own named family — a failure mode that reports success — whose three members are recorded in orchestrator/SKILL.md: the claude effort typo, the codex model flag before its subcommand, and the terminal that reports its shell.

The latent hazard is already in the code, not hypothetical.

Line 621 builds a board reader with the fixture alone. It works today only because the one tracker that has a board is also the one whose board read needs no repository. Nothing in the signature says so, and nothing fails if that stops being true.

Solution

Pass the adapter, not the four values it is made of. main() constructs one Tracker and hands it to wake(). wake() hands it to phase(), which hands it to merge_requested() and to deliver(). Four parameters collapse into one at every level, three constructions collapse into one, and the seam between the tick and its tracker becomes a single object rather than a convention repeated at three depths.

Benefits

Locality. Which tracker a tick talks to becomes one fact in one place. Today it is four facts restated at six call sites, and one of those sites restates only one of the four.

Leverage. A fifth tracker value — a token, a timeout, a retry count — is one field on the adapter. Today it is a new parameter on wake, on phase, on deliver, on wake_targets and on three constructor calls.

The interface becomes the test surface. This is the part that pays for the change. phase() today is unreachable from a test except through argv, because assembling its 15 arguments in the right order is worse than shelling out. Give it a Tracker and it becomes a plain function a test calls directly, with a fixture-backed adapter passed in. The 65 subprocess cases that cover the predicate can then cover it in-process, and thresholds.coverage in config stops being permanently blank.

No ADR conflict.

ADR 0040 says the tracker is one adapter behind both seams. This candidate uses that adapter more, not less. ADR 0018 says the watch is a stateless seam, and passing an adapter adds no state to it. Nothing here reopens a decision.

Candidate 2

The close is two writes the caller must order

Worth exploring

Files

  • scripts/tracker.py — close_argv line 319, closing_note_argv line 333
  • scripts/close_item.py — tracker_parts line 336, note_part line 379

Problem

One tracker records a closing reason inside the close command. The other has no such flag, so the reason is its own write and it must go first. The adapter holds both halves, and it holds neither the ordering rule nor the fact that the two are one operation. The caller does: note_part() asks for the note argv, tests whether it came back empty, and tracker_parts() then splices it in front of the close by hand at line 376.

return [label, *([note] if note else []), close, card_part(args, tracker)]
                ^ the ordering rule, living in the caller

Apply the deletion test to closing_note_argv. Deleting it does not move the complexity, it deletes a method whose whole job is to answer “does this tracker need a second write?” — a question the caller should never have to ask.

Solution

One method returns the ordered writes: close_writes(item, comment) gives [note, close] on one tracker and [close] on the other. The caller iterates. It never learns that one tracker needs two writes, and the order cannot be got wrong because there is no order to assemble.

Benefits

Locality: the ordering rule sits next to the two commands it orders. Testability: one case asserts the returned list per tracker, and no case has to build a plan to prove the order.

The honest limit, and why this is not Strong.

Step 7 needs each write as its own resumable part, with its own status and its own idempotency read. note_part() reads the comments to see whether the reason is already posted, and only the seam knows what a part is. So the branch shrinks, and it does not vanish.

Candidate 3

One board recipe, two implementations of it

Worth exploring

Files

  • scripts/tracker.py — board_status line 246, board_card line 260, _board_list_argv line 392

Problem

Two methods ask the same board read for two facts that arrive in the same answer, and they extract them two different ways. board_status reads the JSON and walks the items in Python. board_card pushes a --jq filter into the CLI and reads a bare string. Same recipe, two extraction styles, and the jq selector is a second copy of the match rule that the Python walk already implements.

board_status  read_json(…) then for entry in data["items"]: if number == item
board_card    run(…, jq=".items[] | select(.content.number==<item>) | .id")

The match rule is “the card whose content number is this item”. It is written twice, in two languages. A change to the board recipe in docs/agents/issue-tracker.md has to land in both, and only one of them is covered by a test that reads real JSON.

Solution

One method, board_item(item, project, owner), returns the pair (status, card_id) from one read and one walk. The two existing methods become one-line readers of that pair, or they go away and their callers take the pair.

Locality: the match rule exists once. Testability: one fixture answer proves both facts, and the jq string stops being an untested second parser. The saving is consistency, not calls: the two facts are wanted by two different seams at two different moments, so nothing merges into one network round trip.

Candidate 4

The test double lives inside the production class

Worth exploring

Files

  • scripts/tracker.py — 5 if self.fixture is not None branches, plus write line 418

Problem

Five of the adapter’s six fact methods open with a fixture branch, and write() opens with a sixth that appends to a .writes log instead of running. So every read has two implementations in one method, and a reader of item_facts has to hold three code paths at once: the fixture, one CLI and the other.

def item_facts(self, item):
    if self.fixture is not None:  # path 1, tests only
        …
    if self.cli == GLAB:          # path 2
        return self._glab_facts(item)
    return self._gh_facts(item)   # path 3

Solution

Split the reads from the argv builders. A FixtureTracker satisfies the same interface and answers from the file. The production class holds no test branch. The argv builders — the half that has no fixture branch already — stay shared, so nothing is duplicated to buy this.

Before / After

Before — 3 paths per read

After — 2 paths, one interface

Benefits

Depth: the interface stays the same size and the implementation behind it gets simpler, which is the definition. Locality: the fixture format is documented in one docstring and would then also be implemented in one place.

Contradicts ADR 0040, and only just worth reopening.

ADR 0040 chose “one class, and the tracker is four values on it”, and the fixture is one of those four. Two children of story #143 then built on that choice, and CLAUDE.md requires a new ADR to narrow it. Reopen only if a third tracker arrives, because that is the point where five branches per method becomes seven. Until then this is a real smell with a load-bearing decision behind it.

Candidate 5

write() re-implements run()

Speculative

Files

  • scripts/tracker.py — run line 62, write line 418

Problem

Both hold the same four lines: run the command, check the exit code, raise TrackerError with the same message format. run()’s own docstring says it is “the one place that reports a failed command, so no builder repeats it”, and write() repeats it 350 lines later.

raise TrackerError(f"{' '.join(argv)} failed: {proc.stderr.strip()}")   # line 71
raise TrackerError(f"{' '.join(argv)} failed: {proc.stderr.strip()}")   # line 429

Solution

The fixture guard stays, and the tail becomes run(argv) with its result dropped. Three lines go.

Before

After

Benefits

The message format cannot drift between a read and a write. That is the whole benefit, and it is small. This is a three-line tidy inside one commit of other work, not a piece of architecture.

Top recommendation

Candidate 1 — give the tick predicate a callable interface

Take this one first, for three reasons that the other four do not have.

  1. 1.It is the only candidate that unblocks a measurement. thresholds.coverage in docs/agents/orchestrator.md is blank with a written reason, and this is the change that retires that reason.
  2. 2.It removes a live instance of this repo’s own named failure family. 15 positional arguments in one forward is a reorder that runs, passes and prints a plausible line.
  3. 3.It reopens no decision. It uses ADR 0040’s adapter harder, and it needs no new ADR. Candidate 4 is the one that would need one.

Candidates 2 and 3 are small, safe and independent. They fit inside whichever commit next touches those methods. Candidate 5 is a tidy, not a ticket.

Layer 5 is advisory. It holds no exit code, so it fails no push and no merge (ADR 0033). Vocabulary from orchestrator/CONTEXT.md and the /codebase-design skill: module, interface, depth, seam, adapter, leverage, locality.
