1 · worker_state.py is two modules sharing one file

Strong

scripts/worker_state.py · scripts/test_worker_state.py

The problem

The file holds two concerns that share almost nothing.

  • The watch. The process check, the completion signal, the gate record, the stall, the Position and the transition writer. Eighteen filesystem and subprocess touches.
  • The queue and the start gate. The start gate and the whole tracker-graph walk, from parent_edges to queue_plan, plus the board report. This half touches the filesystem exactly once, to fire the spawn command. It is otherwise a pure graph algorithm over one tracker read.

The proof the file has no internal order: the Touch set block sits in the middle of the watch region, and its only callers are 1200 lines away in the queue half. claim sits among the transition writers and has one caller, the spawn. main() is 365 lines with 23 argument definitions behind six subparsers, so touching one subcommand's flags means reading all six.

The solution

Split the file at the banner that already divides it. One module keeps the watch and its three subcommands. A second keeps the queue, the start gate and its three subcommands. Move the Touch set block and claim to the queue module, where their only callers live. The two share the tracker adapter, the duration parser and the argument helpers, and nothing else.

The benefit

Locality: a queue change touches one file with no process-check vocabulary in it, and a stall change touches one file with no story-tree vocabulary in it. Leverage: the queue half becomes a pure function of one tracker read, so its tests need no worktree fixture, no fake git repo and no fake agent process. Today they carry all three because they share one suite. About 60 tree-walk tests become fast unit tests over a fixture list. Each --help stops carrying the other half's contract.

3 · Two unreachable features: the abandon path, and the parent-link command

Strong

scripts/close_item.py · scripts/tracker.py · their two test files

The problem

--abandon is a complete second path through the close seam: its own plan builder, two exit codes of its own, 60 lines of module docstring, 42 mentions in the seam and ten tests. Nothing invokes it. No seam, no reference file, no ADR, no CONTEXT.md term. The case it exists for is live — the spawn refuses at the readiness gate — but that refusal returns an exit code and nothing then abandons the worktree. So by the repo's own rule that every claim traces to a reference file or an ADR, it has no home.

The parent-link command in the tracker adapter is the same shape, smaller: zero production callers, five test call sites. ADR 0065 asserts that one command writes both representations of the parent edge, so it cannot write only one. Nothing calls that command, so a session writes the two by hand and the guarantee the ADR claims does not hold.

The friction: about 200 of the close seam's 1072 lines serve a path no flow reaches, so every reader of the close transaction reads the abandon branch to learn it is not theirs. The seam's build function branches on an attribute that may not exist, purely so the dead path cannot break the live one.

The solution

Pick one per feature. For the abandon path: wire it to the readiness-gate refusal the docstring names, and give it a term plus an ADR — or delete the path, its two exit codes, its ten tests and its docstring. No flow has asked for it in the two waves since it landed, so delete is the likelier right answer, and a later item can re-add it with a caller attached. For the parent-link command: have the item-writing flow call it, which is what ADR 0065 assumes, or delete it and amend that ADR, because its claim is currently false.

The benefit

Locality: the close seam drops to about 870 lines that all describe one transaction, and the defensive branch disappears with the coupling it encodes. Leverage: the exit-code table shrinks from seven meanings to five, so a caller reads only codes it can receive. Tests improve by subtraction: ten tests and five argv assertions stop pinning behaviour nobody can trigger. This is the clearest case of tests asserting implementation in the repo — two of them assert the exact argument list of a command with no caller.

4 · The hook plane has no shared reader, so two file formats have four parsers

Strong

hooks/refuse.py · hooks/record.py · hooks/context.py · scripts/worker_state.py

The problem

Three readers are byte-identical across all three hooks: the project directory, whether the repo is orchestrated, and the item number. Beyond that:

  • The gates: block of the config is parsed twice, with the same 20-line block walk and the same regular expression declared in two files.
  • The work-state label table is parsed twice. The two copies differ by one docstring sentence and one inverted condition.
  • head_sha is implemented four times, and two of them disagree on the failure value. That is a live inconsistency, not only duplication.
  • The Gate record format has three independent implementations across two directories: one writer and two readers that disagree on whether to keep every run or only the newest per command. The staleness rule is written twice, each with its own copy of the seven-character prefix constant.

One of the two readers even documents the coupling in prose, pointing at the other copy. A comment that points at a second copy is the repo telling you where the seam should be. Adding a key to the gate record line, or a fourth layer, means finding four files across two directories. A change that updates three of four ships a hook that denies a push the tick would have passed.

The solution

One small module holds what a hook needs to know about a repo: the project root, whether the repo is orchestrated, the item this worktree implements, the gate commands, the work-state labels, and HEAD. All three hooks import it. A second small module owns the Gate record: the write, the read, the malformed-line rule and the at-HEAD test, with one prefix constant. The push denial and the unproven-gates outcome both call it and keep their own message wording, which is the part that legitimately differs. Resolve the head_sha disagreement while there.

The benefit

Locality: the gate record format gets one home in code to match the one home it already has in prose. Leverage: adding a layer becomes one edit, and the four-way head_sha split becomes one function with one documented failure value. Tests: today the malformed-line rule is tested twice against two implementations that can drift. After, one suite of about a dozen cases covers the format and both callers inherit it, and the hook suites shrink to the three denials and the one append, which is what they are actually about.

The deletion test says deepen. Deleting any one hook concentrates nothing, because the duplication stays. Deleting the duplicated set and giving it one home concentrates two file formats in one place each.

5 · The dispatcher's merge-train row dead-ends, and two reference files fell off the graph

Strong

orchestrator/SKILL.md · references/reporting.md · references/examples/run.md · references/prompt.template.md

The problem

The dispatcher routes a merge-train ask to references/reporting.md. That file answers the close question well, with a five-row table and the rule against running the close seam by hand. It never mentions the merge-train seam. It carries one bullet on how to format a train report and nothing on how to produce one. The seam appears in no reference file at all: only in the glossary, four ADRs, and its own 117-line module docstring.

So a session asked to run a train follows the dispatcher to reporting.md, finds nothing runnable, and must know to read the glossary's last sentence and then open a Python file. Four hops, where hop two is a dead end. The old 1578-line body printed the invocation directly.

The same rewrite orphaned the end-to-end worked example. It has 12 inbound links from the README, the glossary, the setup skill and three ADRs — and zero from the skill body, transitively. A session that loads the dispatcher never learns the worked example exists. The prompt template is in the same position, reachable only through the spawn seam, which is defensible but worth stating on purpose rather than by accident.

The solution

Give the train what the close already has: a short section that names the seam invocation, says the seam mutates nothing, states the park rule in one line, and points at the module docstring for the ordering. Then the dispatcher's promise is kept at the first hop. Add one line to the dispatcher pointing at the worked example, in the spawn section, because that is the flow it walks. Add one line saying the prompt template is the spawn seam's input and not a file a session reads.

The benefit

Locality: a named request in the dispatcher table reaches its answer in one hop, which is the property that makes a dispatcher worth having. Leverage: the train's contract stays in the seam docstring where ADR 0037 put it, so this adds a pointer of three or four lines and not a second copy. Tests: the link suite already walks every markdown file, so add the reachability assertion — every row target in the dispatch table resolves to a file that names the seam or flow the row promises. That turns "the dispatcher keeps its promises" from a review finding into a gate.

7 · The tracker adapter carries two interfaces over one concept

Worth exploring

scripts/tracker.py · scripts/test_tracker.py

The problem

The adapter exposes two parallel surfaces. One says "do the tracker operation". The other says "hand me the argument list and I will run it". Production callers, counted outside the module and its tests:

close_argv          prod 0   test 10
closing_note_argv   prod 0   test  3

pr_read_argv        prod 1   test  2

The first two are internals of the close writer. They are public purely because the tests read them, which is the definition of a test asserting implementation rather than behaviour. One test asserts a literal command list, where the behaviour under test is "a close takes one command on one tracker and two in a fixed order on the other" — which the close writer already expresses.

There is a second shape question. About 220 of the adapter's 515 code lines are GitHub Projects GraphQL, and the card write opens by returning early on the other CLI. One third of the adapter is single-implementation code sitting inside a genuinely two-implementation adapter, which makes the interface read as if boards were cross-tracker when they are not. The per-CLI branching elsewhere is a real adapter: about 20 branches with two live implementations and 37 assertions for the second CLI.

The solution

Make the argument-list surface private where it has no production caller, and let the tests assert through the close writer, which is what ADR 0069 made the contract. Keep the three that the close plan genuinely prints rather than runs, and say so in a docstring sentence, because right now the two surfaces look like an accident. Separately, consider whether the board block wants its own module behind one narrow entry, so the adapter's remaining surface is the part both trackers implement.

The benefit

Locality: a reader sees one surface per concept, and one clearly labelled second surface for plan printing, with the reason stated. Leverage: the argument-list assertions collapse from thirteen call sites on two methods to a handful on the close writer, so changing how a close is spelled on one tracker stops breaking tests that were never about that spelling. Tests improve from pinning command strings to pinning the ordering guarantee ADR 0069 actually promises.
