Desired state · orchestrator-skills · target version 1.0.0

Start it with a drag, finish it with a merge

This page holds one architecture, and it obeys three laws. The tracker is the only control surface. Every gate is a command with an exit code, recorded by a machine and enforced by a machine. An agent runs only where a machine cannot decide.

The problem this design fixes is not a missing feature. It is that the orchestrator session had to remember too much. A 1578-line skill asked one model to hold a nine-outcome table, two label families, a board mirror and a five-layer gate matrix in its head, every turn. It skipped rows. So this design moves each rule out of the model's head and into one of three places: a label on the tracker, a Python seam with an exit code, or a hook that says no.

You act twice per work item

Act one starts it: the ready-for-agent label, and the card dragged into the board's To do column. Act two finishes it: you merge the PR on GitHub. Nothing between those two acts needs a session open, a chat verb, or a second column drag. The merge is the signal, so there is no label to remember and no queue to approve.

The one sentence that drives every cut

A rule a model must remember is a rule that will be skipped. So every rule in this design has an owner that cannot forget: a label, an exit code, or a denial. Where no such owner exists, the rule is deleted rather than written down again.

The session writes no label

This is the structural fix for the bug you reported. A status the session never writes is a status it cannot forget to write. Every label write belongs to a seam.

Nothing writes the board

The board is read at the start and never written. Your drag into To do is the only column move in the design. When the item closes, the board's own built-in workflow moves the card to Done, at no cost to us.

A seam performs, a hook refuses

A hook never mutates the tracker, never merges and never spawns. It answers yes or no, or it injects a fact. That keeps a hook fast, safe and easy to test. There is one named exception, and the hook section holds it.

The tracker is the API

one family, four values

The phase:* family is deleted. It existed to cache where an item was. Every fact it cached is already on disk or on the tracker, so the seam computes the position instead of reading a label that can disagree with the truth. to-merge is deleted too, because the merged PR says the same thing and you cannot forget to do it. One family remains, and it never stacks.

Four bugs the deleted labels take with them

Two stacked work states. One function owns the swap, and one test asserts exactly one label after every transition. An undelivered wake burning its window. There is no delivery left, so no marker and no window. An answered round firing again. Rounds are gone with the review loop. A card dragged to a column nobody read. There is one column now, and the tick reads it every minute.

What you give up, stated plainly

The machine no longer orders your merges, and no longer parks a branch that conflicts. You see the conflict in the PR, where GitHub already shows it. That is the trade for deleting a label, a seam from the loop, a park rule and a whole close-verb table. The order hint is still available when you want it, as a verb.

Every gate is a command with an exit code

recorded and enforced by a machine

A gate had three weak points. A model decided whether it passed. A model wrote the record that proved it. And nothing stopped a push that skipped it. This design closes all three. A gate is a command from the config, its exit code is the verdict, a hook writes the record, and a hook blocks the push. No model reports a gate, and no model can pass one by claiming it did.

Gate The command When it runs What enforces it
static and tests gates.quick after each edit, and before each commit the record hook writes the line, and the push is denied while it is not green at HEAD
whole repo gates.full before the push same
deep gates.deep when the PR is open the record hook writes the line, and to-review is denied while it is not green
infra policy gates.infra on a plan, where the repo has one same as deep
architecture depth no command once per story Not a gate. It has no exit code, so it stops nothing. It is a verb you run, and it sits in The story, once.

A blank command is a dropped box

A gate whose command is blank in the config loses its checklist box before the prompt is sent. A repo with no mutation runner ships no deep box. That stays a supported configuration.

The record has one writer

.orchestrator/gates-<item>.jsonl is written by the record hook and by nothing else. Command, exit code, UTC timestamp and head_sha. A stale sha reads as not green, so a commit after a run means the gate runs again.

The five-layer matrix stays, as config help

The matrix says which tool belongs in quick, full and deep for a given language. That is guidance for writing the config. The skill knows only the commands the config names.

It wakes an agent only to spawn a worker, and it talks to you only when it refuses.

Two roofs bound the cost, and the lower one wins. max_stories is 2, so no more than two Story runs are live at once. max_workers is 4, so no more than four Workers are live across every run. The two roofs must not multiply, so the worst case is 4 live workers and never 2 times 4. A Story run holds its slot until the parent closes, story proof included. The tick starts nothing while either roof is full.

One re-prompt, then a human

The count is the number of Re-prompt: comments on the item, so it survives a restart and you can read it. The first one resets the worker's context and sends the unchecked boxes again. The second attempt writes needs-human instead. There is no ladder of models and no stall diagnosis.

Three hooks, shipped with the plugin

the layer that can say no

A hook is the only part of this stack that can refuse a command before it runs. The plugin manifest gains one key, "hooks": "./hooks/hooks.json", so the enforcement installs with the skill and needs no step from you. Each hook is stdlib-only Python with a test suite, the same bar the seams hold.

Hook Event What it does Which failure it kills
context.py SessionStart
startup, resume, clear, compact		 Exports the plugin root from CLAUDE_PLUGIN_ROOT. Reads whether this session is an orchestrator or a worker. Injects the item's current facts: the label, the checklist position, and whether the gate record is green. A session working from memory, and a session that lost the facts to a compaction. It also deletes the plugin-root glob, because the hook is handed the path.
refuse.py PreToolUse · Bash Denies three commands. git push while the gate record is not green at HEAD. A work-state label write from any session, because only a seam writes one. The teardown command outside close_item.py. A gate passed by claim. A label written by hand. A teardown out of order.
record.py PostToolUse · Bash Where the command that just ran is a configured gate command, appends one line to .orchestrator/gates-<item>.jsonl with its exit code and head_sha. A forgotten record, which used to read as a failed gate. And a faked record, which used to read as a green one.

The one exception to the law

record.py writes a file, and every other hook only answers. The reason is named: a record a model writes is a record a model can fake. This is not a mutation of the tracker. It is an append-only note of what a command already did.

Every hook exits fast when it does not apply

Hooks fire in every session on the machine once the plugin is installed. So the first check is the repo marker: docs/agents/orchestrator.md, or an .orchestrator/ directory. No marker means no output and no cost.

Two hooks are skipped on purpose

A Stop hook could reconcile the board. Not needed, because the session writes no label and nothing writes the board. A merge guard is not needed either, because you are the one who merges. Add either only if a real failure asks for it.

Each seam takes the tracker as flags and reads no config file, which is why the same code runs on GitHub and on a self-hosted GitLab with no wrapper.

It still updates every dependency, still asks one question at a time with a recommendation, and still installs what is missing instead of printing a command. What changes is what it writes. Three things it wrote no longer exist, and four things the new planes need have no other owner.

The one thing setup cannot do for you

Nothing writes the board any more, so the board's own built-in workflow is what moves a card to Done. Setup reads whether item closed to Done is enabled and says so plainly. It cannot turn it on, because that switch is not in the API. This is the only external dependency in the whole design.

Setup rides the waves, and never gets one of its own

Each edit above lands in the same change that alters what it configures. Setup must never write a config the loop cannot read. A setup that still writes phase:* into a repo whose tick deleted the family produces a repo that was configured wrong on purpose.

Two drifts to fix while it is open

The body still says only the Python gate column has landed. Go and TypeScript landed too, and the config template already knows it. So detection reads go.mod and tsconfig.json as well, and the install loop reads all four tool tables instead of one. Two open items already own that fix, one per family, so this design adds none.

Where an agent is needed

one inside the loop

An agent is needed here

  • The worker. It reads a work item and writes code. No script can do that. It is the whole reason the loop exists, and it is the only agent inside the loop.
  • Writing the work item, before the run. /to-spec, /to-tickets and /triage turn a conversation into items and labels. They also write the ## Touches block, because the person who splits the work is the only one who knows the paths before the code exists.
  • Answering needs-human. That label exists to reach you.
  • The story proof and the depth review, once per story. Both are in the next section.

Merge conflicts left this list. Not because a machine handles them, but because you merge now. Run /resolving-merge-conflicts yourself when you want the help.

The prompt becomes a template, and stays reviewed

A rendered prompt looks like a downgrade. It is not. prompt-improver reviews the template once, at build time, instead of every prompt at run time. The template takes the item title and body, the checklist, the gate commands from the config, and the skill named by the type label. Those are the only values a per-item prompt ever carried. The test is the guard: the template renders against a fixture item, and the test fails when a field goes missing. A prompt a model wrote by hand had no such check.

The story, once

two flows · one reference file

Both parent flows stay, and both get shorter. They live together in references/story-flows.md, because they run in one sequence at one moment: the close of the last child. The parent wears the same work-state family as any other item. No parent-only label is added.

The story proof

One fresh worker in its own worktree, cut from the default branch. That tree is the first place every child's merged code sits together. It drives playwright-cli, writes one spec, wires the spec into gates.full, and opens a PR. The proof is the green test command, and not a note a model reads. That is what makes it deterministic. It reaches the parent through the same five outcomes as any other item, and you merge its PR the same way.

The depth review

/improve-codebase-architecture, run in the main checkout after the proof. Its report is saved to docs/refactor-opportunities/ and committed. Candidates rated Strong become work items. It stops nothing. It holds no exit code, so it is not a gate. A candidate still untriaged is work to report, and never a close the machine refuses.

Where the parent close stops

A failed proof leaves the parent open and files each failure as a work item. It runs no depth review. The last child of a story is also the commit that bumps the version in .claude-plugin/plugin.json. Minor for a story that changed a contract, patch for a docs-only story.

What the body keeps

Who this session is. The one law: never write code here. A dispatch table, six rows, of what a request reaches. The three judgement flows, one paragraph each. Five safety bullets. That is the whole file.

Reference files: 11 stay, 2 are new, 2 go

New: story-flows.md and hooks.md. Gone: merge-train.md, because the train is a verb with a docstring. Merged into one worked trace: examples/run.md. The five harness files and the four tool files keep every per-harness detail, so the body branches on none of it.

The rule that keeps it small

A claim in the body must be needed on every turn. Anything else is a reference file or a seam docstring. The docstring is already the source of truth for each seam's table, and the body restates none of it.

The setup skill shrinks for a different reason. orchestrator-setup/SKILL.md goes from 686 lines to about 300, and none of that is a move to a reference file. It is the review question, the gate profile question, the board write half and the terminal title being deleted outright. Setup is never in context on a worker turn, so its length costs nothing per turn. It shrinks because the things it configured no longer exist.
