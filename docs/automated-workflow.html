Target design · orchestrator-skills

Start a story, and the workflow runs itself

The plugin is at 0.32.0. This page holds one design, and it obeys two rules. The tracker is the only control surface: a label, a card and a block in the item body. An AI agent runs only where a machine cannot decide. Everything else is a Python seam with an exit code.

You act twice per user story, and never once per child. The first act starts the story, and it is two facts: the ready-for-agent label, and the card in the board's To do column. The second act merges, and it is the to-merge label. The automation then finds every unblocked child of that story and works it, up to two roofs. No chat verb, and no session that must stay open.

The Ready column is your own lane. An item that carries the label and sits in Ready is never started, so a groomed item you mean to do yourself is safe on the same board. Both facts are needed, and the gate is quiet on purpose.

The run holds exactly one agent per work item: the worker that writes the code. Adversarial review adds a second one, and it stays off by default. The story proof adds one more, once per user story and never once per item. No other step is an agent, because no other step needs judgement. A label swap is a lookup. A merge order is a computation. A teardown is a file operation. Each one belongs in a script that a test can fail.

This design supersedes the plan that used a machine-started session. Read What this design retires for the reasons, and skill-state-and-roadmap.html for the skill as it stands today.

Your two acts, per story

a label and a card

A step stays human for one reason only: a machine cannot supply the fact. The first act is consent to spend money. The second act says a person read the diff. Neither fact exists on disk, so neither can be computed.

Act once on the parent, and every child follows. A story of ten children costs two acts in total, and no child is ever labelled. Label a leaf task instead and only that task runs.

Act On the board Or from the CLI What it starts
1 · start
two facts		 The story already carries ready-for-agent. Drag its card to To do gh issue edit N --add-label ready-for-agent
+ one Projects v2 field write		 The queue tick descends to every unblocked child and spawns them, under both roofs. A blocked child waits until its blocker closes
2 · merge Drag the reviewed card to To merge gh issue edit N --add-label to-merge
glab issue update N --label to-merge		 The item tick runs the merge train over every to-merge item, then closes and tears down each one

Every act is idempotent. Two writes of the same label are one state, and a card already in a column stays there. So a retry is safe, and a script can apply them from a loop over five item numbers.

A tracker with no board keeps working. Where docs/agents/issue-tracker.md names no board, the label alone is the whole gate. That is the fallback the merge queue already takes, so local markdown and a board-less GitLab project stay supported targets.

The train computes one order across all five, and merges them in it. You resolve a file once, and never twice. Each PR gets a comment that names its place in that order.

The chat verb still works

work on 151 stays as a manual override, and it does the same label write plus an immediate spawn. It needs no card in To do, because the ask itself is the second fact. It is a convenience, and never the mechanism. The two facts are the trigger, so the flow works with no session open at all.

How you take it back

No drag ever removes a label. The promotion runs one way, board to label, so a card dragged back out of To do changes nothing. To stop work, remove ready-for-agent, or write needs-human, and comment why. Once a worker holds the item the card reads In progress anyway, so a drag back is already too late.

The loop closes on itself. A close feeds the queue tick, and the queue tick spawns the next child. So a story of ten children needs one start act and one merge act, and no other input. The merge act can cover all ten at once, with one shell loop.

Two gates now stand between a ready story and a spawn, and both are cheap. The touch check is an fnmatch compare over two lists of paths. The roof check is two integers. Neither one is an agent, and a no on either sends the tick back to sleep with nothing spent.

The three violet boxes belong to another story. Story #163 adds them, and nothing in them is built yet. Two of them run an agent, and both run once per user story and never once per work item. So the per-item cost stays one green box, and a ten-child story pays for two more agents in total.

1 · the tracker is the state

No seam keeps state between ticks. Each tick reads the labels, the cards and the files again. So a reboot loses nothing, and a repeat cannot fire: the transition swapped the label, and the next tick reads the new one.

2 · a seam refuses, and never warns

A dirty tree stops a teardown. A missing gate record stops a review transition. A conflict stops a merge. Each one is a non-zero exit and a comment on the item, and never a warning the run walks past.

3 · one agent, one job

The worker writes code. It writes no label, moves no card, opens no schedule and merges nothing. So a worker that dies mid-run costs one worktree, and never a corrupt state.

The control surface · every fact, and what it fires

this table is the API

Read this table as the whole interface. A fact fires exactly one deterministic response. Two label families stay mutually exclusive. A work-state label swaps, and never stacks. A phase label swaps, and never stacks.

Two facts are not labels, and both are new. A card in the To do column is the second half of the start gate. A ## Touches block in the item body decides whether two children can run at the same time. Every other column is still a copy of the work-state label, and the board writes nothing back there (ADR 0009).

Three labels are new, and two of them replace judgement with a lookup. role:* and verb:* are what let a script spawn a worker without an agent to classify the item first. Each one has a default, so an unlabelled item still runs.

The start gate is the one place two facts say one thing, and that is deliberate. An item holding one fact and not the other is not an error, and nothing repairs it: that is how you park a groomed story. The cost is that a forgotten drag reads as an empty queue, so the queue report names every item that holds one fact and not the other.

Where an agent is needed, and where it is not

one agent in the run

An agent is needed here

The worker. It reads a work item and writes code. No script can do that. It is the whole reason the loop exists.

The adversarial reviewer, where review.enabled is true. A verdict is a judgement. It is off by default in this repo, so the normal run has one agent.

Writing the work item, before the run. /to-spec, /to-tickets and /triage turn a conversation into items and labels. You start those, and they end before the first ready-for-agent. They also write the ## Touches block, because the person who splits the work is the only one who knows the paths before the code exists.

The proof worker, once per user story. Story #163 adds it, and it is not built yet. A browser run is judgement, so it is an agent. It runs once per story, so it does not change the per-item cost. The tick still runs no agent.

One case is deliberately not an agent. A merge conflict is judgement, so an agent could resolve it. This design parks it for you instead. A machine that guesses what your merged file means is the one failure nobody can see in a diff. Run /resolving-merge-conflicts yourself when you want the help.

The prompt becomes a template, and stays reviewed

A rendered prompt is the one part of this that looks like a downgrade. It is not. ADR 0006 keeps holding, and it moves up one level: prompt-improver reviews the template once, at build time, instead of every prompt at run time. The template takes the work item title and body, the checklist from references/checklist.template.md, the gate commands from the config, and the skill named by the verb:* label. Those are the only values a per-item prompt ever carried.

The test is the guard. The template renders in a test, against a fixture work item, and the test fails when a field goes missing. A prompt an agent wrote by hand had no such check.

No path exits 0. Exit 0 is what loads the schedule's own model, and no tick needs one. So both schedules hold a prompt and a provider that never run. The only tokens the loop spends belong to the worker.

The queue tick now reads the board every minute. That is one Projects v2 query per tick, repo-wide, and it is the price of the second fact. Before this change the board read was a side effect of the reconcile pass. Now the start path depends on it, so a board read that fails is a tick that spawns nothing and says so.

Code Meaning
1Nothing is due, or a transition was applied and the run is quiet again
2New. A seam refused. The item wears needs-human, and one comment says why
3The worktree is gone, so there is nothing left to watch
4A worker was spawned, or an agent was woken

Code 5 retires with the wake ladder. A transition no longer needs a target to accept a line, because the seam applies it itself.

Three bugs the label kills

#155 two stacked work states. The seam owns the swap, and one test asserts that exactly one work-state label is present after every transition. A prose rule in four places becomes one function.

#156 an undelivered wake burns its window. There is no delivery, so there is no marker and no window. The transition either applied or it did not, and the next tick reads the truth from the labels.

#157 an answered fix round re-fires. The phase:fix-<k> label records the round in flight, on the tracker, where any tick and any restarted session reads it.

All three are one class of bug: a fact that lived in a marker file, in a delivery, or in a session's memory. Move each fact to a label, and the bug has nowhere to live.

Four seams own the whole run

stdlib only · tested

Three exist. One is new. Every one is stdlib-only Python with a test suite, because that is the bar this repo already holds for close_item.py, worker_state.py and merge_train.py.

The count is four, and it stays four. Story #163, the story proof, adds no seam. It spawns one more worker and writes two artifacts, so the existing seams carry it.

One tracker adapter behind all four

Four seams now read and write the tracker, so the adapter stops being a nice idea. Story #143 becomes a hard dependency of this design, not a parallel track. gh and glab both need one verified recipe per operation: read labels, write labels, read the body, post a comment, close an item, move a card.

Every seam takes the tracker as flags, and reads no config file. That rule already holds for the tick, and it is why the same code works on GitHub and on a self-hosted GitLab with no wrapper. The one place the config is read is the schedule that the setup writes.

Safety · what an unwatched script may do

read this one twice

A deterministic loop is safer than an agent loop in one way, and more dangerous in another. It is safer because every act is a tested function with an exit code. It is more dangerous because nothing hesitates. So the permissions are written down, and a test holds each one.

A seam may do this unwatched

  • Swap a label, and move a card.
  • Cut a worktree, and start a harness process.
  • Send a rendered prompt to a live worker.
  • Merge a PR, where the item wears to-merge. That label is a human act, and it is the standing authorization (ADR 0037).
  • Tear down a worktree with a clean tree, and remove its schedule.
  • Post a comment, and close an item whose PR is merged.
  • Spawn every unblocked child of a story you started, under both roofs. The story is the ask, and the children are what it asked for.
  • Post and rewrite the order comment on a PR/MR. It reports the plan, and it authorises nothing.

A seam may never do this

  • Merge an item that does not wear to-merge. There is no other path to a merge.
  • Resolve a conflict. It parks the branch and comments the paths.
  • Remove a worktree with uncommitted work. Step 6 refuses.
  • Write ready-for-agent. Only you and triage do, so no loop can start work you did not ask for. A child of a story is never labelled either, so this rule needs no exception.
  • Move a card into To do or To merge. Both columns are your intent, and a seam that writes one would authorise its own work.
  • Remove a label because a card moved. The promotion runs one way only.
  • Remove needs-human. That label is a full stop, and only you lift it.
  • Spawn past either roof, or spawn a user-story item for the work itself.
  • Spawn two items whose touch sets overlap, where parallel_check is touches.

The one cost bound

Money is spent in exactly one place: a spawned worker, and its re-prompts. So the cost bound is three numbers, and all three live in the config: max_stories (2), the worker cap (4), and the re-prompt bound per item. The two roofs do not multiply. The lower one wins, so the worst case is four live workers and not eight. A worker that stalls twice is re-spawned once, one rung up, and never a third time. The re-spawn is recorded as a label, so a restarted loop cannot forget it and try again.

A dirty tree still stops the re-spawn, because a re-spawn tears down. That is the only ask left inside the automatic part, and the ask exists to protect uncommitted work.

Say the cost out loud

This repo stops being mostly Markdown. CLAUDE.md opens with that sentence today, and this design retires it. Much of On the wake in orchestrator/SKILL.md becomes Python, and the skill body shrinks to the parts an agent still reads: how to be a worker, and how to write a work item.

That is the trade you are buying. A rule in prose is cheap to write and impossible to fail. A rule in a seam costs a test and a review, and it cannot drift. You asked for deterministic, and this is what deterministic costs.

One consequence is worth naming. The plugin becomes useful to a repo that never opens an orchestrator session at all. Two acts and two schedules are the whole interface, so a CI job or a cron can drive it.

The story start adds one more cost, and it is on you. A ## Touches block is only as good as the person who writes it. An empty block costs parallelism, and a wrong one costs one park. Neither one costs a wrong merge, because the test-merge is still the real check.
