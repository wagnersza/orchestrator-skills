1. Why v2

v1 works, but it supports every combination: three workspace tools, five harnesses, three trackers, four model roles, five quality-gate layers, adversarial review, a merge train, a board mirror, and 65 ADRs. It also rebuilds signals that orca now gives for free: done, stuck, and asking a question. v2 supports one combination and leans on orca for everything else.

2. The shape in one picture

The automation decides when, the script decides what, and orca and GitHub hold the facts. The main session never waits on workers. It answers four verbs and goes idle.

3. Labels: the only state

At any moment an issue carries exactly one state label. A transition swaps one label for another in a single gh issue edit. Every transition is written by the script, never by a worker.

TransitionTriggerWrites
ready-for-agent → in-progresstick or start N finds an eligible issue and a free slot--add-assignee @me --add-label in-progress --remove-label ready-for-agent, then worker-start
in-progress → ready-for-humanworker_done --outcome succeeded in the mailbox, with a PR that is open and says Closes #Nlabel swap; worker-release
in-progress → needs-humanworker_done --outcome failed, an ask or escalation, or liveness exited with no worker_donelabel swap; issue comment holding the worker's own text; worker-stop; worktree kept
needs-human → ready-for-agentthe human answers in an issue comment and relabelshuman act. The next claim reuses worktree issue-N with a fresh worker that reads the latest comments
ready-for-human → closedmerge N, or the tick sees the PR already mergedteardown (see §7); Closes #N closes the issue
No automatic re-prompt. v1 re-prompted a stalled worker once before calling a human. v2 sends every stuck signal straight to needs-human, so no tokens are spent on a worker that has already lost its way.

Eligibility, exactly

eligible(issue) =
     issue.state == open
  && "ready-for-agent" in issue.labels
  && (issue.assignees is empty || issue.assignees == [me])
  && issue.issue_dependencies_summary.blocked_by == 0     // native dependencies
  && no open issue in a "Blocked by: #n" body line         // the mattpocock fallback

The assignee check is the lock between two humans: one human's orchestrator never takes an issue claimed by the other's.

4. The tick

One orca automation per repo, orchestrator-tick, cron * * * * *. Its --precheck is node <abs>/scripts/orchestrator.ts tick. The precheck exits non-zero on every path, so orca records each run as skipped and never starts the automation's agent. This is the v1 trick, kept on purpose.

tick():
  if !acquireLock(".orchestrator/tick.lock")    // stale after 5 min
    exit 1
  try
    cfg  = readConfig("docs/agents/orchestrator.md")
    run  = readRunId(".orchestrator/run.json")

    // 1. observe: drain the mailbox (non-blocking), then apply each message
    for msg in orca orchestration check --run run --json:
      N = issueOf(msg.dispatch)                 // from the Task title "issue-N"
      match msg.type:
        worker_done succeeded -> toReadyForHuman(N); worker-release
        worker_done failed    -> toNeedsHuman(N, msg.summary); worker-stop
        question | escalation -> toNeedsHuman(N, msg.body);    worker-stop
      ack msg

    // 2. catch silent deaths
    for row in orca orchestration worker-list --run run --json:
      if row.liveness == exited and no worker_done for row.dispatch
        toNeedsHuman(N, "worker exited without reporting")

    // 3. merged on github.com?
    for N in issues labelled ready-for-human:
      if prOf(N).merged -> teardown(N)

    // 4. parents
    for P in parents labelled in-progress:
      if all children closed -> gh issue close P --comment summary

    // 5. fill free slots
    free = cfg.max_workers - count(issues labelled in-progress, excluding parents)
    for issue in eligibleQueue() while free > 0:
      if isParent(issue) -> claimParent(issue)   // no worker, no slot
      else               -> start(issue); free--
  finally
    releaseLock()
  exit 1                                        // always: no agent runs

The order inside a tick matters. Observing first frees slots before filling them, so a worker that finished this minute makes room for the next issue in the same tick.

5. Parents and children

A parent is an issue with native sub-issues, the shape /to-tickets produces. The user-story label is also accepted. A parent never gets a worker of its own.

  1. The human puts ready-for-agent on the parent. The tick claims it: assign @me, in-progress. The parent takes no worker slot.
  2. A child starts only if it carries its own ready-for-agent, meaning it already holds all the context an agent needs, and only once nothing blocks it. A child without the label waits, even when unblocked.
  3. Each child then follows the leaf flow: its own worktree, its own PR to base, its own review and merge.
  4. When a child merges, its dependents unblock, and the next tick starts them if they carry the label.
  5. When every child is closed, the tick closes the parent with a summary comment that lists the PR of each child.
So the label on a child is the human's "this one has enough context" and the label on the parent is the human's "run this story". A labelled child runs whether or not its parent is claimed. The parent's claim only makes the story's progress visible and closes it at the end.

6. The worker contract

The script calls orca orchestration worker-start --spec <rendered> --task-title issue-N --worktree new-top-level --name issue-N --base-branch <base> --agent <agent> --model <m> --effort <e> --run <run>. On resume it calls --worktree name:issue-N instead. Orca injects its own lifecycle preamble (Task and Dispatch IDs, the exact worker_done and ask commands), so our template only has to say what the work is.

You are working on GitHub issue #{N}: "{title}", on branch issue-{N}.

1. Read the issue and every comment: gh issue view {N} --comments
2. Run /implement on it.
3. Commit in slices: one logical change per commit, Conventional Commits.
4. Push, then open a pull request (not a draft) against {base}.
   Write its body with the `pr` skill, and put "Closes #{N}" in it.
5. Never add or remove labels, and never merge.
6. If you are blocked on a decision only a human can make, use the
   orchestration `ask` command from your preamble and stop.
7. When finished, send worker_done --outcome succeeded with the PR URL,
   or --outcome failed with the reason.
{resume? "This issue was resumed. Read the latest comments first: they answer why you stopped."}
{note?}
  • No issue body is pasted in. The worker reads it itself, so the prompt stays small and is never stale.
  • No test command in the template. /implement already runs the full suite at the end, then /code-review.
  • {note} comes from a manual start N --note "…". It is the one place the main agent still adds its own words to a prompt.
  • Model: cfg.model/cfg.effort, or cfg.heavy_model/cfg.heavy_effort when the issue carries cfg.heavy_label.

7. Merge and teardown

This reverses v1's ADR 0057 ("no session merges"). In v2, the human's explicit merge N is the authorisation.

merge(N):
  pr = gh pr list --search "Closes #N" --state open
  refuse unless pr is mergeable and review is not CHANGES_REQUESTED
  refuse unless worktree issue-N is clean (no uncommitted work)
  gh pr merge pr --squash --delete-branch
  confirm gh pr view pr --json state == MERGED
  teardown(N)

teardown(N):                   // also called by the tick when merged on github.com
  orca orchestration worker-release   (if a dispatch is still held)
  orca worktree rm name:issue-N
  gh issue edit N --remove-label ready-for-human
  // "Closes #N" already closed the issue; close it explicitly if not

Teardown runs only after GitHub confirms the merge. A refusal prints one line that says why, and changes nothing.

8. The script — scripts/orchestrator.ts

TypeScript, run directly by Node 24 (type stripping is built in). No build step, no runtime dependencies. Erasable syntax only: no enum, no namespace, no parameter properties.

SubcommandCalled byDoesExit
installskill, "setup"idempotent setup (§9)0 / 1
tickthe automation precheckobserve → catch deaths → merged → parents → fill (§4)always 1
start N [--note "…"]skill, "work on N"eligibility check, claim, worker-start; also starts a parent's labelled unblocked children0 / 1 with reason
statusskill, "status"compact table: issue · label · liveness · PR URL; then the ready queue0
merge Nskill, "merge N"refusals, squash merge, teardown (§7)0 / 1 with reason

Internal shape

scripts/
├── orchestrator.ts        # CLI entry + the five subcommands, ~400–600 lines
│     sh(cmd, args)        # the one seam: spawnSync → {code, stdout, stderr}
│     gh.*  orca.*         # thin typed wrappers around sh() returning parsed JSON
│     eligible / isParent / issueOf / render / transitions
└── orchestrator.test.ts   # node --test; a fake sh() replays canned gh/orca JSON

Everything goes through one sh() function, and the tests swap it out. No fixture git repos, so the suite runs in well under a second, against v1's ~35 s.

9. Config and install

docs/agents/orchestrator.md

This file stays in the mattpocock docs/agents/ convention. It holds one fenced JSON block that the script reads, with prose around it that explains each field:

{
  "agent": "claude",
  "model": "sonnet",
  "effort": "medium",
  "heavy_label": "heavy",
  "heavy_model": "opus",
  "heavy_effort": "high",
  "max_workers": 3,
  "base": "main"
}

orchestrator.ts install (idempotent)

  1. Check orca status, gh auth status and Node ≥ 22.18.
  2. Check mattpocock-skills is installed, and install mattpocock's pr skill if it is missing. It lives in the in-progress bucket, which the plugin does not ship: npx skills@latest add mattpocock/skills --skill=pr.
  3. Create the labels in-progress and needs-human if they are missing. ready-for-agent and ready-for-human come from the mattpocock triage setup, so create them only if absent.
  4. Write the default config block if docs/agents/orchestrator.md has none.
  5. Create the orca Run (orchestration run-create) and save its id in .orchestrator/run.json, which is gitignored.
  6. Create the automation orchestrator-tick with the precheck as an absolute path, because orca runs it later in a shell that saw no assignment.
  7. Run one tick by hand and print its outcome as proof the precheck works.

10. The skill surface

orchestrator/SKILL.md, under ~60 lines. Every action is one script call, and that is the token budget.

User saysSession runs
"work on N", "start N", "implement #N"node …/orchestrator.ts start N [--note]. On the first use in a repo with no automation, run install first
"status", "what's running", "what next"node …/orchestrator.ts status
"merge N", "merge and teardown N"node …/orchestrator.ts merge N
"setup the orchestrator"node …/orchestrator.ts install

Two hard rules in the body: never implement in this session, and never write a state label by hand, because the script owns every transition. Any other request is answered freehand.

12. Glossary and ADRs

New orchestrator/CONTEXT.md — the terms

TermMeaning
OrchestratorThe main session. It answers the four verbs and never implements.
WorkerOne claude session started by orca on one issue, in its own worktree.
TickOne run of the automation's precheck. It observes, transitions and fills slots, then exits non-zero so no agent runs.
State labelThe one label that holds an issue's work state: ready-for-agent, in-progress, ready-for-human or needs-human.
ClaimAssigning an eligible issue to the person running the orchestrator and moving it to in-progress.
EligibleOpen, ready-for-agent, unassigned or assigned to me, nothing blocking it.
ParentAn issue with sub-issues (or user-story). It is claimed and closed, but never worked.
ChildA sub-issue of a parent. It runs exactly like a leaf issue.
SlotOne of max_workers places for a live worker. Parents take none.
ResumeA fresh worker on an existing issue-N worktree after a needs-human round trip.
TeardownReleasing the worker, removing the worktree and dropping the state label, after a confirmed merge.

New ADRs

#DecisionRejected
0001The automation precheck is the whole tick. One automation per repo, always exiting non-zero.A blocking check --wait in the main session (the session must stay alive, and every wake costs tokens); one automation per item (v1: leaks, and a repoint step).
0002orca orchestration is the done/stuck signal. worker_done, ask and liveness drive the transitions; no re-prompt.Checklist files, terminal idle scraping, PR polling, one automatic re-prompt.
0003Labels are the only state. One state label per issue; only the Run id persists locally.A local state file (it drifts from GitHub); the Projects board mirror.

14. Build order

Each step is one commit slice, and each leaves the branch working.

  1. Tag v1.0.0 on main.
  2. Strip v1. Delete everything marked delete; set plugin.json to one skill. (Nothing runs between this commit and step 4, so release only after step 9.)
  3. Tooling. package.json, tsconfig.json, Makefile quick, .gitignore.
  4. sh() + typed wrappers + config reader, with tests.
  5. Eligibility + parent detection + claim + start N (render + worker-start), with tests.
  6. tick: lock, mailbox drain, death catch, parent close, slot fill, with tests.
  7. merge N + teardown, and the tick's merged-on-GitHub path, with tests.
  8. status + install, with tests.
  9. Docs. SKILL.md, CONTEXT.md, ADRs 0001–0004, README, CLAUDE.md, docs/agents/orchestrator.md; version: 2.0.0.
  10. Dogfood. install in this repo, label one small issue, and watch it through every state, including a forced needs-human and a resume.

15. Risks and open edges

  • The mailbox outside a coordinator terminal. The tick is not an orca terminal. It addresses the Run with --run <id>. Slice 4 must prove that orchestration check --run without --wait returns and acks from a plain shell. If it does not, fall back to worker-list plus worker-show per dispatch, which is still JSON and still costs zero tokens.
  • An unacked message replays. check replays the oldest delivery until it is acked. A tick that crashes after the label swap but before the ack sees the message again. Every transition must be idempotent: swapping to a label the issue already has is a no-op.
  • Mapping a dispatch back to its issue. Use the Task title issue-N and the worktree name issue-N. Never parse the free-text summary.
  • The pr skill is beta (mattpocock's in-progress bucket) and "can change or disappear". If it does, the template line falls back to "a PR body with Summary, Evidence, Merge Danger".
  • A repo with no tests. /implement assumes a typecheck and a test suite. In a repo without them the worker still runs, but its evidence is thinner. That is the target repo's problem, not v2's.
  • Resume on a worktree that has gone away. If the human deleted issue-N while it sat in needs-human, start from scratch on a new worktree. The branch, if pushed, still holds the work.
  • Two machines, one human. "Assigned to me" lets the same person's two orchestrators both claim an issue. That is out of scope for v2.0: run one install per repo per person.
