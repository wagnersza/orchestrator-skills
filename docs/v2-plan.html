orchestrator v2

A rewrite from scratch, not a refactor. One loop driven by an orca automation that costs no tokens. The tracker's state labels are the only state. Harnesses, trackers and model roles stay configurable, and the plan cuts everything else. The plan came out of the grilling session on 2026-10-12.

1. Why v2

v1 works, but it carries a lot of machinery around the core loop: a per-item automation plus a queue automation, a 1,500-line worker watch, a close transaction, a merge train, a board mirror, five quality-gate layers, adversarial review, a prompt-improver pass, a simple-english pass, and 65 ADRs. It also rebuilds signals that orca now gives for free: done, stuck, and asking a question. v2 keeps what v1 got right (many harnesses, many trackers, configurable model roles, a precheck tick that costs no tokens) and cuts the rest.

2. The shape in one picture

The automation decides when, the script decides what, and orca and the tracker hold the facts. The main session never waits on workers. It answers four verbs and goes idle.

3. State labels: the only state

At any moment an issue carries exactly one state label. On GitHub and GitLab it is a label; on the local tracker it is the Status: line. A transition swaps one for another in a single tracker call. Every transition is written by the script, never by a worker.

TransitionTriggerWrites
ready-for-agent → in-progresstick or start N finds an eligible issue and a free slottracker.claim(N): assign me + in-progress − ready-for-agent; then worker-start
in-progress → ready-for-humanworker_done --outcome succeeded in the mailbox, and the PR/MR is open (or, on local, the branch has commits ahead of base)state swap; worker-release
in-progress → needs-humanworker_done --outcome failed, an ask or escalation, or liveness exited with no worker_donestate swap; an issue comment holding the worker's own text; worker-stop; worktree kept
needs-human → ready-for-agentthe human answers in an issue comment and relabelshuman act. The next claim reuses worktree issue-N with a fresh worker that reads the latest comments
ready-for-human → closedmerge N, or the tick sees the PR/MR already mergedteardown (see §9)
No automatic re-prompt. v1 re-prompted a stalled worker once before calling a human. v2 sends every stuck signal straight to needs-human, so no tokens are spent on a worker that has already lost its way.

Eligibility, exactly

eligible(issue) =
     issue is open
  && issue.state == "ready-for-agent"
  && (issue.assignees is empty || issue.assignees == [me])
  && tracker.blockers(issue) are all closed

The assignee check is the lock between two humans: one human's orchestrator never takes an issue claimed by the other's.

4. The tick

One orca automation per repo, orchestrator-tick, cron * * * * *. Its --precheck is node <abs>/scripts/orchestrator.ts tick. The precheck exits non-zero on every path, so orca records each run as skipped and never starts the automation's agent. This is the v1 trick, kept on purpose.

tick():
  if !acquireLock(".orchestrator/tick.lock")    // stale after 5 min
    exit 1
  try
    cfg     = readConfig("docs/agents/orchestrator.md")
    tracker = trackers[cfg.tracker]
    run     = readRunId(".orchestrator/run.json")

    // 1. observe: drain the mailbox (non-blocking), then apply each message
    for msg in orca orchestration check --run run --json:
      N = issueOf(msg.dispatch)                 // from the Task title "issue-N"
      match msg.type:
        worker_done succeeded -> toReadyForHuman(N); worker-release
        worker_done failed    -> toNeedsHuman(N, msg.summary); worker-stop
        question | escalation -> toNeedsHuman(N, msg.body);    worker-stop
      ack msg

    // 2. catch silent deaths
    for row in orca orchestration worker-list --run run --json:
      if row.liveness == exited and no worker_done for row.dispatch
        toNeedsHuman(N, "worker exited without reporting")

    // 3. merged on the tracker?
    for N in tracker.list(state = ready-for-human):
      if tracker.isMerged(N) -> teardown(N)

    // 4. parents
    for P in tracker.parents(state = in-progress):
      if all tracker.children(P) closed -> tracker.close(P, summary)

    // 5. fill free slots
    free = cfg.max_workers - count(in-progress, excluding parents)
    for issue in eligibleQueue() while free > 0:
      if tracker.isParent(issue) -> claimParent(issue)   // no worker, no slot
      else                       -> start(issue); free--
  finally
    releaseLock()
  exit 1                                        // always: no agent runs

The order inside a tick matters. Observing first frees slots before filling them, so a worker that finished this minute makes room for the next issue in the same tick.

5. Parents and children

A parent is an issue that has children, the shape /to-tickets produces. The user-story label also marks one. A parent never gets a worker of its own.

  1. The human puts ready-for-agent on the parent. The tick claims it: assign me, in-progress. The parent takes no worker slot.
  2. A child starts only if it carries its own ready-for-agent, meaning it already holds all the context an agent needs, and only once nothing blocks it. A child without the label waits, even when unblocked.
  3. Each child then follows the leaf flow: its own worktree, its own role, its own PR to base, its own review and merge.
  4. When a child merges, its dependents unblock, and the next tick starts them if they carry the label.
  5. When every child is closed, the tick closes the parent with a summary comment that lists the PR of each child.
So the label on a child is the human's "this one has enough context" and the label on the parent is the human's "run this story". A labelled child runs whether or not its parent is claimed. The parent's claim only makes the story's progress visible and closes it at the end.

6. Roles, harnesses, models

Three roles, each a {harness, model, effort} set in config. The role is picked per spawn and deterministically, because the tick has no agent to judge with:

role(issue, manual?) =
  manual --role given                    -> that role       // "work on N" may pass one
  issue has label cfg.role_labels.heavy  -> heavy
  issue has label cfg.role_labels.light  -> light
  issue's "## Touches" block lists ≥ 3   -> heavy          // v1's countable signal
  otherwise                              -> medium

A manual work on N lets the main agent read the issue and pass --role. That is the only time a role costs tokens, and only when the human asks in person.

The script clamps an effort and reports the clamp. It refuses a config that pairs a model with a harness that cannot launch it, such as an openai model under claude.

8. The worker contract

The script calls orca orchestration worker-start --spec <rendered> --task-title issue-N --worktree new-top-level --name issue-N --base-branch <base> …<harness start flags> --run <run>. On resume it calls --worktree name:issue-N instead. Orca injects its own lifecycle preamble (Task and Dispatch IDs, the exact worker_done and ask commands), so our template only has to say what the work is.

You are working on issue {ref}: "{title}", on branch issue-{N}.

1. Read the issue and every comment: {tracker.viewCommand}
2. {harness.skill("implement")} on it.
3. Commit in slices: one logical change per commit, Conventional Commits.
4. {tracker.reviewStep}
     github → Push, open a PR (not a draft) against {base}. Write its body
              with {harness.skill("pr")}, and put "Closes #{N}" in it.
     gitlab → the same, as a merge request.
     local  → Leave the work on branch issue-{N}. Write the
              {harness.skill("pr")} body under "## Comments" in {path}.
5. Never change the issue's state or labels, and never merge.
6. If you are blocked on a decision only a human can make, use the
   orchestration `ask` command from your preamble and stop.
7. When finished, send worker_done --outcome succeeded with the PR/MR URL
   (or branch name), or --outcome failed with the reason.
{resume? "This issue was resumed. Read the latest comments first: they answer why you stopped."}
{note?}
  • No issue body is pasted in. The worker reads it itself, so the prompt stays small and is never stale.
  • No test or review step in the template. implement already runs the suite, then code-review.
  • Skill names are rendered per harness ({harness.skill(…)}): /implement on claude, "use the implement skill" elsewhere. Setup installs those skills into every harness the config names (§11).
  • {note} comes from a manual start N --note "…". It is the one place the main agent still adds its own words to a prompt.

9. Merge and teardown

This reverses v1's ADR 0057 ("no session merges"). In v2, the human's explicit merge N is the authorisation.

merge(N):
  refuse unless the state is ready-for-human
  refuse unless the worktree issue-N is clean (no uncommitted work)
  tracker.merge(N)               // github/gitlab: refuse unless mergeable and not
                                 //   changes-requested; local: refuse unless the
                                 //   main checkout is clean and on base
  confirm tracker.isMerged(N)
  teardown(N)

teardown(N):                     // also called by the tick when merged on the tracker
  orca orchestration worker-release   (if a dispatch is still held)
  orca worktree rm name:issue-N
  tracker: drop ready-for-human; close if "Closes #N" did not (local: Status: resolved)

Teardown runs only after the tracker confirms the merge. A refusal prints one line that says why, and changes nothing.

11. Setup and config

The interview lives in the orchestrator-setup skill. The side effects live in orchestrator.ts install, so a re-run is always safe.

The orchestrator-setup skill (rewritten)

  1. Tracker. Read docs/agents/issue-tracker.md. If it is missing, run mattpocock's setup-matt-pocock-skills first.
  2. Roles. Ask for a cost profile, which fills in all three {harness, model, effort} sets at once. Then let the human change any one of them.
  3. Limits. max_workers (default 3) and base.
  4. Dependencies. Check and install: orca, Node ≥ 22.18, the tracker CLI (gh / glab, none for local), and the CLI of every distinct harness across the three roles.
  5. Skills into every harness. Install the mattpocock skills the worker uses (implement, tdd, code-review, diagnosing-bugs, and pr from the in-progress bucket) into each harness the config names, in one call:
    npx skills@latest add mattpocock/skills -s implement,tdd,code-review,diagnosing-bugs,pr -a <agent,…> -g -y
    Then confirm each harness lists them.
  6. Write the config block, then run orchestrator.ts install.

orchestrator.ts install (idempotent)

  1. Create the state labels in-progress and needs-human if they are missing. ready-for-agent and ready-for-human come from the mattpocock triage setup, so create them only if absent. Also create the role labels. The local tracker needs no labels.
  2. Create the orca Run (orchestration run-create) and save its id in .orchestrator/run.json, which is gitignored.
  3. Create the automation orchestrator-tick with the precheck as an absolute path, because orca runs it later in a shell that saw no assignment.
  4. Run one tick by hand and print its outcome as proof the precheck works.

orchestrator/SKILL.md, under ~60 lines. Every action is one script call, and that is the token budget.

Two hard rules in the body: never implement in this session, and never write a state label by hand, because the script owns every transition. Any other request is answered freehand.

14. Glossary and ADRs

New orchestrator/CONTEXT.md — the terms

TermMeaning
OrchestratorThe main session. It answers the four verbs and never implements.
WorkerOne agent session started by orca on one issue, in its own worktree, on the harness and model its role names.
HarnessThe agent CLI a worker runs in: claude, codex, cursor, pi or copilot.
TrackerWhere issues live: GitHub, GitLab or local markdown.
RoleThe class of an issue that picks its {harness, model, effort}: heavy, medium or light.
TickOne run of the automation's precheck. It observes, transitions and fills slots, then exits non-zero so no agent runs.
State labelThe one value that holds an issue's work state: ready-for-agent, in-progress, ready-for-human or needs-human. A label on GitHub and GitLab, a Status: line locally.
ClaimAssigning an eligible issue to the person running the orchestrator and moving it to in-progress.
EligibleOpen, ready-for-agent, unassigned or assigned to me, nothing blocking it.
ParentAn issue with children (or user-story). It is claimed and closed, but never worked.
ChildAn issue under a parent. It runs exactly like a leaf issue.
SlotOne of max_workers places for a live worker. Parents take none.
ResumeA fresh worker on an existing issue-N worktree after a needs-human round trip.
TeardownReleasing the worker, removing the worktree and dropping the state label, after a confirmed merge.

17. Risks and open edges

  • pi and copilot under supervision. They start through terminal create + worker-start --terminal, not --agent. Slice 5 must prove this binds a supervised Dispatch with the same mailbox and preamble. If it does not, those two harnesses fall back to dispatch --inject, which orca marks unsupervised. Their done/stuck signal would then come from worker-list liveness only, plus the worker running orca orchestration send itself.
  • First-run trust dialogs. codex and copilot ask "trust this folder?" in a new directory, and v1 needed a two-step send to answer it. Check whether orca's agent launch handles it. If not, harnesses.ts carries the answer keystroke per harness.
  • Skills on non-claude harnesses. The skills CLI agent ids and each harness's way of invoking a skill must be checked once per harness. If a harness cannot load a skill, the template inlines a three-line "tdd → test suite → review your diff → commit" fallback for that harness only.
  • The mailbox outside a coordinator terminal. The tick is not an orca terminal. It addresses the Run with --run <id>. Slice 4 must prove that orchestration check --run without --wait returns and acks from a plain shell. If it does not, fall back to worker-list plus worker-show per dispatch, which is still JSON and still costs zero tokens.
  • An unacked message replays. check replays the oldest delivery until it is acked. A tick that crashes after the state swap but before the ack sees the message again. Every transition must be idempotent: swapping to a state the issue already has is a no-op.
  • Local tracker ids are not unique across features. 01 exists in every feature directory, so the local id is always <feature>/NN, and the worktree name carries both parts.
  • The local merge touches the main checkout. merge N refuses unless that checkout is clean and on base.
  • The pr skill is beta (mattpocock's in-progress bucket) and "can change or disappear". If it does, the template falls back to "a PR body with Summary, Evidence, Merge Danger".
  • Mapping a dispatch back to its issue. Use the Task title and the worktree name issue-N. Never parse the free-text summary.
  • Resume on a worktree that has gone away. If issue-N was deleted while it sat in needs-human, start from scratch on a new worktree. The branch, if pushed, still holds the work.
  • Two machines, one human. "Assigned to me" lets the same person's two orchestrators both claim an issue. That is out of scope for v2.0: run one setup per repo per person.
