Five waves from here to there

The target design lives in architecture.html. This page holds the other half: where the repo stands today, what happens to each of the 37 open work items, and the order that gets from one to the other without a half-migrated repo.

Why wave 1 comes first, and not the rewrite

Wave 1 is the only wave that pays off against the current design. The hooks make gates deterministic without touching one line of the loop. So if the migration stalls after wave 1, the repo is still better off, and nothing is half-migrated. Every later wave depends on a piece wave 1 lands: the callable predicate, or the record hook.

The one-way doors

and what protects each one

Three changes are hard to walk back. Each one has a guard, and each guard is the reason the wave order is what it is.

Deleting the phase:* family

Every open item wearing one loses it in a single item, so the vocabulary is never half migrated. The guard: land wave 2 with no worker in flight. Read the queue first. An item at to-review is safe. An item at in-progress is not.

A seam that writes the tracker on a schedule

A wrong transition now lands every minute, with nobody watching. The guard: needs-human plus a hard rule that a tick applies at most one transition per run. Plus the callable interface from wave 1, so each transition has its own test.

A schedule that starts workers

This is the biggest one. A loop can spawn until the disk fills. The guard: the two roofs, the touch-set gate, and one item per tick. All three are already specified in story #178, which is why that story is wave 4 and not wave 1.

The rollback for each wave

Wave 1: delete the hooks key from plugin.json. Everything else keeps working. Wave 2: a revert, and the labels are re-added by hand on the few open items. Wave 3 and 4: remove the schedule, and the loop falls back to the manual flow the skill body still holds until wave 5. That is the real reason the rewrite is last. The prose is the rollback plan for every wave before it.
